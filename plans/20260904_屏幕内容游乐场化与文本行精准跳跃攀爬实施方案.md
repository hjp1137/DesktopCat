# 屏幕内容游乐场化与文本行精准跳跃攀爬实施方案

## 1. 背景与目标
用户明确提出了核心愿景：
> “小猫将屏幕上的文本、图片、边框等作为实体位置，可以进行攀爬、行动等，而空白处对它来说，就是空气，所以它只能跳跃。由此把屏幕显示的内容变成了小猫的游乐场。”

目前小猫左右行走为主、缺乏与屏幕内容关联性的根因在于：
1. **文本行缺失实体踏板**：旧版视觉感知在 1/4 降采样下平滑了文本，并设置了 60px 过滤；UIA 遇到多行大文本块只生成外框单线，导致屏幕大面积文本区在物理世界中是空的。
2. **短平台安全边界截断**：`surface_fusion_builder.gd` 和 `navigation_node.gd` 采用死板的 48px 和 14px 边距，短文本被过滤或标记为不可通达。
3. **导航与自主调度偏好地面**：缺乏针对密集短行距（20~50px）的阶梯小跳（Hop）和把屏幕文本作为优先攀爬游玩目标的驱动力。

## 2. 核心架构与修改要点

### 2.1 视觉几何感知增强（`visual_perception.py` & 配置）
- 引入**前台活动窗口行级投射分析器（Window Content Text-Line Profiler）**：
  - 针对活动窗口以更高精度采样，计算每行的水平梯度方差；
  - 提取文字行特征波峰，识别出每一行文字的垂直 Y 坐标与横向起止 $[x_1, x_2]$；
  - 生成覆盖文字行的青绿色水平踏板，将过滤长度降至 24px（覆盖 2-3 个汉字）。

### 2.2 UIA 控件文本段落行级拆分（`ui_automation_perception.py`）
- 针对高度大于 32px 的多行 `Text` / `Document` / `Edit` 元素，依据真实行高或行间距切分为多条文本行踏板；
- 优化遍历深度与超时控制，确保前台窗口文本节点提取完整。

### 2.3 表面融合器与导航节点自适应优化（`surface_fusion_builder.gd` & `navigation_node.gd`）
- 将 `MIN_PLATFORM_LENGTH` 与 `MIN_TEXT_PLATFORM_LENGTH` 调整为 24.0px；
- 平台安全边距计算改为自适应：`safe_margin = minf(14.0, length * 0.2)`，确保短文本段也是合法落脚点；
- 避免对不同 Y 轴行距（如 20~30px）的真实文字行过度融合。

### 2.4 密集梯级小跳与屏幕探索权重强化
- 优化 `platform_navigation_graph.gd`：对上下行距 20~60px、重叠或近邻的文本行，生成低成本、高优先级的 `JUMP_WALK`（梯级跳跃）；
- 在自主探索调度中，增加对高处文本行与图像踏板的探索好奇心权重，驱动小猫从地面逐行跳跃登顶、在段落间闲逛与攀爬。

### 2.5 常态屏幕元素线条展示与剪裁解除
- 根因：Windows 底层 `window_set_mouse_passthrough` 使用 `SetWindowRgn` 强制裁剪了小猫身体以外的视口像素，仅在拖拽时才临时解除裁剪；
- 方案：在 `main.gd` 新增常态展示模式 `show_debug_lines`（默认开启），在非拖拽状态下也解除 Region 剪裁限制，直接展示屏幕文本发光台阶与攀爬立柱；
- 快捷键：绑定 `V` / `F9` 键，支持随时在【全屏线条展示】与【纯穿透小猫模式】之间一键切换。

### 2.6 Win32 智能动态穿透架构（方案 1A）
- 机制：利用 Win32 `WS_EX_TRANSPARENT` 扩展样式实现全屏常驻绘制同时对底层软件 100% 鼠标穿透；
- 动态 Hit-Test：鼠标光标在小猫贴身范围（50px）内时，临时移除 `WS_EX_TRANSPARENT` 允许点击/拖拽小猫；移出后立即恢复穿透，用户可无阻碍点击网页、输入法与桌面应用。

### 2.7 全屏工作窗口感知与打字/浏览实时响应
- 彻底排除自身控制台窗口（`Godot Engine (Console)`），将扫描范围扩展至全屏所有可见应用区域；
- 差分阈值从 16 降至 10，精准识别灰色、低对比度文本行；
- 联动 `check_screen_changed`，在用户打字、页面滚动时以 2~4Hz 动态高频捕获，实时刷新物理台阶。

## 3. 验证方案
1. 运行 Godot 既有全量自动化测试（135+ 项）确保核心物理与导航无回归；
2. 运行 Python 感知行级投射单元测试；
3. 实机启动 `run_desktop_cat.bat` 观察调试线框与小猫实际跳跃游玩行为。

## 4. 2026-09-04 同任务返工与收口方案

### 4.1 返工原因

本轮复核确认，T25 Hybrid 快照目前只写入独立的 `CatPhysicsWorldModel` 调试层，实际碰撞、导航与自主探索仍由旧的 Window、UIA、Visual 融合结果驱动。同时，常态开启 Surface 调试线并把离散表面缝合进鼠标穿透多边形，会造成 Windows 窗口区域裁剪与交互异常。T25 服务还固定抓取主屏幕并按 5Hz 全量编译，存在坐标偏移和重复计算问题。

### 4.2 收口目标

1. 将 Hybrid 稳定表面接入 `SurfaceWorldModel`，作为默认实际物理来源，并沿既有 `surface_world_updated` 信号触发导航图重建；Legacy 保留为显式回退。
2. 统一目标显示器工作区坐标。抓取区域使用工作区原点与尺寸，编译结果使用工作区局部坐标，UIA 和窗口语义先完成同一坐标系转换。
3. 感知端先计算低成本画面指纹。静止画面跳过重型编译，变化时防抖并异步编译；只有最终几何签名变化才提交 Godot。
4. 产品模式默认关闭 Surface 和 T25 调试绘制。鼠标穿透区域只包含小猫自身简单多边形，不再拼接离散平台或墙面。
5. T25 调试图层快捷键改为组合键，避免数字键 `1~8` 抢占既有小猫控制命令。普通数字键继续保持 STOP、移动、跳跃、跑动、坐下等既有行为。

### 4.3 实施顺序

1. RED：先新增 Godot 集成契约测试，证明当前 T25 快照不会进入 `SurfaceWorldModel`、不会触发导航链路，并锁定产品模式及快捷键契约。
2. RED：新增 Python 服务测试，锁定目标工作区元数据、语义坐标归一化和静止帧跳过重型编译行为。
3. GREEN：在融合层增加 T25 活跃表面候选转换，由 Bridge 在接收有效新快照后请求融合；保持 SurfaceWorldModel 为碰撞和导航唯一数据源。
4. GREEN：重构 T25 服务为单次工作区抓取、指纹门控和变化后编译，避免与旧视觉链路重复抓取；后续逐步淘汰重复流水线。
5. GREEN：恢复产品默认隐藏调试绘制和纯小猫穿透多边形，将 T25 图层切换迁移为组合键。
6. REFACTOR：复用既有几何签名、Surface 转换和工作区信息，删除缝合多边形及重复全屏处理分支。

### 4.4 验收门槛

1. Godot 自动测试证明 Hybrid 表面 ID 出现在 `SurfaceWorldModel`，revision 变化后导航图进入待重建状态。
2. Python 单元测试证明相同工作区画面不会重复调用 `ScreenPhysicsCompiler.compile`，变化画面才产生新快照。
3. Python 单元测试证明传入编译器的 UIA 与窗口坐标已转换为目标工作区局部坐标，输出携带工作区元数据。
4. Godot 自动测试证明默认不显示 Surface 调试线，鼠标穿透多边形长度始终等于小猫轮廓，普通数字键仍执行既有控制命令。
5. 全量 Python 与 Godot 回归测试通过；Windows 实机补充目标屏幕切换、网页滚动、静止 CPU、鼠标点击穿透和小猫落脚验证。
